# Golden fixtures

This directory freezes the observable behaviour of Stride's domain logic, so
that a port to another language can be *proved* equal to the Python reference
instead of believed equal to it.

The specification is [`docs/core-contract.md`](../../../docs/core-contract.md).
Read that first; it defines the file formats, the units, the rounding and the
tolerance.

## Layout

| path | what it is |
|---|---|
| `fixtures/*.fit` | the twelve FIT inputs, committed (80 KB), regenerated byte for byte by `make_fixtures.py` |
| `cases.json` | the frozen description of every input: path, SHA-256, size, watch, sport, date |
| `scenarios/readiness.json` | the readiness inputs: the physiology rows and the day to score |
| `scenarios/plan.json` | the plan-engine inputs: the block, the sessions, the activities, the physiology |
| `golden/*.json` | the golden outputs, generated from the reference implementation |
| `fit_writer.py` | a minimal, deterministic FIT writer (profile-driven, using the decoder's own profile) |
| `make_fixtures.py` | the twelve case definitions and the fixture generator |
| `test_fixture_privacy.py` | the guard: every committed position is the synthetic anchor, and none is near the athlete's real routes |

## Running it

```bash
python3 scripts/golden.py --check       # regenerate and compare; non-zero on any drift
python3 scripts/golden.py --generate     # rewrite the golden files
python3 scripts/golden.py --fixtures     # rewrite the FIT fixtures and cases.json
python3 scripts/golden.py --list         # list the cases
```

`--check` is a no-op on the committed tree. That is the point: it is the proof
that the reference implementation is stable, and it is what a port is measured
against.

## The cases

| case | why it exists |
|---|---|
| `mixed_run` | running cadence stored halved, a walking warm-up and a 20 s stand in one file — the segmentation case that matters, and the one where a half-cadence bug hides |
| `hr_gps_run` | a plain outdoor run with heart rate, GPS and six laps: the full fingerprint, with every metric populated |
| `treadmill` | no GPS at all: a port must not assume a position stream |
| `no_cadence` | a watch with no cadence sensor: every cadence metric must be `null`, never `0` |
| `short_effort` | one lap: the thirds are empty, so the drift metrics must be `null` rather than invented |
| `cycling` | a non-running sport whose cadence is **not** halved: 90 rpm stays 90 rpm |
| `low_resolution` | a watch that records every five seconds, with a walk and a stand: the intervals are five seconds wide |
| `hilly` | an elevation profile that climbs 60 m and descends 60 m |
| `gaps` | a paused watch: two 100-second holes in the record stream |
| `real_garmin_run` | the byte format a real watch writes: FIT protocol 1.0, `enhanced_speed`/`enhanced_altitude` instead of `speed`/`altitude`, fields and messages the published FIT profile does not describe, a redefined local message number, and an irregular record stream |
| `real_garmin_gap` | the same real-watch format, with the 204-second hole the real files contain: the distance does not advance across it, the hole is charged to the running, and the laps are not |
| `real_garmin_nulls` | the reserved "no value" sentinels in the fields the importer reads: a sentinel is an absent field, and it is absent *before* any range check |

Plus two non-FIT scenarios: `readiness` (four days: full, poor, no personal
baselines, no data at all) and `plan` (one week of sessions that land on every
verdict the plan engine can produce).

## The three real-watch cases

The nine cases above are shaped by what a *port* might get wrong. The last
three are shaped by what a *watch* actually writes: they were written after
reading thirteen FIT files downloaded from the athlete's own Garmin account
(March 2025 - October 2026).

**The format came from the real files; the data did not.** Every position in
every fixture is fabricated and describes the same point in the South Pacific
(`-35.0, -140.0`), about 15 500 km from the nearest point of the athlete's
real routes and 4 000 km from the nearest coast. Nothing derived from the
real routes is committed — and nothing points at a real place, because the
nine synthetic cases used to start at 12.9716/77.5946, which is the centre
of Bengaluru and 10.7 km from a real route point. `test_fixture_privacy.py`
is what keeps it that way: it fails if a fixture ever carries a coordinate
that is not the anchor, or one inside the athlete's route box.

What the thirteen real files have in common, and what these three cases
reproduce:

* a 14-byte header, protocol version 1.0, profile version 2196, little
  endian, valid header and file CRCs;
* **no** compressed-timestamp headers, **no** developer fields, **no**
  12-byte header and **no** big-endian file — not one of the thirteen uses
  them, so the decoder's paths for those are paths a real watch never takes;
* a record message that carries `enhanced_speed` and `enhanced_altitude` and
  never `speed` or `altitude`;
* a record message that also carries definition numbers (87, 90, 134, 135,
  136) the published FIT profile does not describe;
* global messages (233, 288, 326 ...) the published FIT profile does not
  describe at all, one of them nothing but a four-byte array;
* local message numbers reused and redefined mid-file, and two live layouts
  of the record message at once;
* an irregular record stream: one to fourteen seconds between records, not
  the uniform second the synthetic cases assume;
* a `device_info` message with no `product_name`, so the watch is reported as
  its manufacturer.

To write them, `fit_writer.py` grew three escape hatches: `RawField` (a
field the profile does not know, written with its raw value so it can carry
a sentinel), `FitWriter.raw_message` (a message whose global number the
profile does not know) and `FitWriter.message(...,
local=N, define=False)` (a local message number that is defined once and
reused, or redefined mid-file).

`real_garmin_nulls` adds one more thing the real files contain: the
reserved "no value" sentinel. Every FIT base type has one — `0xFF` for
uint8, `0xFFFF` for uint16, `0xFFFFFFFF` for uint32, `0x7FFFFFFF` for
sint32 — and the reference turns a sentinel into an absent field *before* any
range check. The real lap and session messages carry `avg_speed` and
`max_speed` as `0xFFFF`, so a decoder that reads them as numbers reports a
missing average speed of 65.535 m/s: a plausible number that is not the
athlete's, and one that no range check catches, because 65.535 is inside the
range. `real_garmin_nulls` writes the sentinels into the fields the importer
reads — the speed, the altitude, the heart rate, the cadence, the distance,
the position, the lap and session averages, and the session's total distance
— so the rule stays frozen once the real files are gone. It has two record
layouts, like the real files do: the classic `speed`/`altitude` pair in the
first half and the enhanced pair in the second, because the reference decoder
expands `speed` into a component and a message carrying both would have its
enhanced value shadowed.

## Regenerating a fixture

The fixtures are generated, not captured. `make_fixtures.py` builds them from
literal values — no clock, no randomness — so:

```bash
python3 scripts/golden.py --fixtures   # rewrites the .fit files and cases.json
```

must leave every SHA-256 in `cases.json` unchanged. If it does not, the input
moved and every golden value derived from it is void.
