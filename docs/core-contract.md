# Stride core contract

**Version 1.0 — frozen against the Python reference implementation on 2026-03-11.**

This document is the byte-level specification of Stride's domain logic: the FIT
parser, the segmentation, the fingerprint, the readiness score and the plan
engine. It exists so that a port to another language (Kotlin, Rust, Swift —
the phone needs this logic on the device) can be *proved* equal to the
reference rather than believed equal to it.

The reference implementation is the Python code under `backend/app/`. It is
not modified by this work. Where this document describes something that looks
wrong, it is describing the reference *as it is today*: §10 lists those places
separately, and they are notes, not requirements.

---

## 1. The one command

**The port exists.** It is `crates/stride-fit`, `crates/stride-core`,
`crates/stride-garmin`, `crates/stride-store` and `crates/stride-api`, and
it checks itself with the golden files:

```
cargo test --workspace        # the golden tests are part of it
```

Each crate's golden test reads `backend/tests/golden/golden/<case_id>.json`
and compares against it under the rules in §8. **38 golden assertions** run
in the gate; `cargo test` exits non-zero if any of them moves.

> There was a plan for a `stride-port-check --case <case_id> --out out.json`
> command that a port author would run once per case. **It was never built**:
> the golden tests inside the crates are the command, and they are stronger,
> because they run in the gate with everything else.

The **reference** side of the same contract is the Python implementation, and
its commands are:

```
python3 scripts/golden.py --check      # regenerate everything and compare
python3 scripts/golden.py --generate    # write the golden files
python3 scripts/golden.py --fixtures    # rewrite the FIT fixtures
python3 scripts/golden.py --list        # the cases, with their sizes
```

`--check` exits non-zero if any golden file or any fixture moved. On the
committed tree it is a no-op, which is the proof that the reference is
stable.

The **cases** are the ids in `backend/tests/golden/cases.json`:

| kind | ids |
|---|---|
| a FIT file | `cycling`, `gaps`, `hilly`, `hr_gps_run`, `low_resolution`, `mixed_run`, `no_cadence`, `real_garmin_gap`, `real_garmin_nulls`, `real_garmin_run`, `short_effort`, `treadmill`, `vendor_coros_export`, `vendor_strava_export`, `vendor_wahoo_export` |
| a scenario | `readiness`, `plan` |

`readiness` and `plan` take their inputs from
`backend/tests/golden/scenarios/readiness.json` and
`backend/tests/golden/scenarios/plan.json` respectively; the other cases take
their input from the FIT file named in `backend/tests/golden/cases.json`.

## 2. The inputs

`backend/tests/golden/cases.json` is the frozen description of every input:

| field | meaning |
|---|---|
| `case_id` | the case name, and the golden file's name |
| `file` | path to the FIT file, relative to the repository root |
| `sha256` | SHA-256 of that file's bytes |
| `bytes` | its size |
| `sport` | the FIT `session.sport` value in the file |
| `device` | the watch, from `device_info.product_name` |
| `watch` | how the watch sampled (every second, every five seconds, paused) |
| `start` | the first record's timestamp, ISO-8601 UTC |
| `date` | the athlete-local date of the run |
| `notes` | what the case is for |

The FIT files are committed (**119,859 bytes** in total, 15 files) and are
regenerated byte for byte by `backend/tests/golden/make_fixtures.py`, which
is driven by the FIT profile the reference decoder itself uses. Nothing in them is random and
nothing reads the clock, so the SHA-256 in `cases.json` is meaningful: if a
fixture is regenerated and the hash moves, the input moved and every golden
value that depends on it is void.

A new case's id sorts **after** the existing ones. The recorded rows of the
API golden (`crates/stride-api/tests/fixtures/api_golden.json`) are numbered
in the order the fixtures are seeded, and a case that sorted first would
renumber every recorded activity — a diff nobody can read.

### 2.1 What the port must read out of a FIT file

Only these messages are used, and only these fields:

| message | fields |
|---|---|
| `file_id` | `serial_number` (becomes `external_id`) |
| `device_info` | `product_name`, else `manufacturer` (becomes `device`) |
| `record` | `timestamp`, `position_lat`, `position_long`, `altitude`, `enhanced_altitude`, `heart_rate`, `cadence`, `distance`, `speed`, `enhanced_speed` |
| `lap` | `total_elapsed_time`, `total_timer_time`, `total_distance`, `avg_speed`, `max_speed`, `avg_heart_rate`, `max_heart_rate`, `avg_cadence`, `max_cadence`, `total_ascent`, `total_descent` |
| `session` | `sport`, `total_elapsed_time`, `total_timer_time`, `total_distance`, `avg_speed`, `max_speed`, `avg_heart_rate`, `max_heart_rate`, `avg_cadence`, `max_cadence`, `total_calories`, `total_ascent`, `total_descent` |

FIT decoding rules that matter:

* `position_lat` / `position_long` are **semicircles**:
  `degrees = round(semicircles * 180 / 2^31, 7)`.
* `distance` is in centimetres (scale 100); `speed` is in millimetres per
  second (scale 1000); `altitude` is `(raw / 5) - 500` metres (scale 5,
  offset 500); `total_elapsed_time` and `total_timer_time` are milliseconds.
* `speed` is preferred; `enhanced_speed` is the fallback. `altitude` is
  preferred; `enhanced_altitude` is the fallback.
* A missing field is *absent*, not zero. The reference treats a field whose
  value is out of range as absent: heart rate outside 0–300, cadence outside
  0–300, speed outside 0–150 m/s, altitude outside −1000–10000 m, distance
  outside 0–10 000 000 m.
* **The FIT invalid sentinel is absent, and this is not the same thing as
  "out of range".** Every FIT base type has a reserved value that means
  *no value*:

  | type | the invalid value |
  |---|---|
  | `uint8` / `uint16` / `uint32` | all bits set — `0xFF`, `0xFFFF`, `0xFFFFFFFF` |
  | `sint8` / `sint16` / `sint32` | the most positive value — `0x7F`, `0x7FFF`, `0x7FFFFFFF` |
  | `string` / `byte` | a zero byte |
  | `float32` / `float64` | `NaN` |

  A decoder that reads `0xFFFF` as a number turns a **missing session
  average speed of 65,535** into **65.535 m/s** — a plausible number that is
  not the athlete's, and one that no range check would catch, because
  65.535 is inside the range. The nine synthetic fixtures never exposed it;
  the real watch files did, on the first run.

  The rule: **a sentinel value is an absent field, and it is absent before
  any range check is applied.**
* Timestamps are seconds since 1989-12-31T00:00:00Z. **They are UTC.** The
  reference implementation converts them through the *host* timezone (a bug,
  see §10.1), so the harness pins `TZ=UTC`; a port must treat FIT timestamps as
  UTC unconditionally.

## 3. The output format

### 3.1 File format

UTF-8, LF line endings, two-space indent, one key per line, a trailing
newline. Object keys are in the order given below — **never sorted**: the
order is part of the contract. Numbers are JSON numbers; there is no
`NaN`, no `Infinity`, and no trailing `.0` is added to an integer-valued
float.

`null` is the only representation of "absent". There is no sentinel value: a
missing heart rate is `null`, never `0`.

### 3.2 Per-case golden file (`golden/<case_id>.json`)

```jsonc
{
  "case_id":    "mixed_run",
  "fixture":    { "file", "sha256", "bytes", "sport", "device", "watch", "start", "date" },
  "import":     { ... §4 },
  "fingerprint":{ ... §5 }
}
```

### 3.3 Readiness golden file (`golden/readiness.json`)

```jsonc
{ "scenarios": [ { "id", "description", "day", "baselines", "readiness" }, ... ] }
```

### 3.4 Plan golden file (`golden/plan.json`)

```jsonc
{ "scenario", "range", "sessions": [ ... ], "adherence": { ... } }
```

## 4. Import and segmentation

`import` is the result of parsing the FIT file with the reference importer.

### 4.1 `import.activity`

The scalar fields of the canonical activity, in this order:

`external_id`, `source` (always `"garmin_fit"`), `name` (the file name with
`_` and `-` replaced by spaces, trimmed), `sport_type`, `description`,
`start_time` (ISO-8601 UTC, `+00:00`), `local_date` (`YYYY-MM-DD`, the UTC
date of `start_time`), `day_of_week` (English weekday name), `distance_m`,
`moving_time_s`, `elapsed_time_s`, `elevation_gain_m`, `avg_hr`, `max_hr`,
`calories`, `avg_cadence`, `max_cadence`, `avg_speed_ms`, `max_speed_ms`,
`perceived_exertion`, `device`, `gear`, `is_trail`, `is_commute`,
`running_time_s`, `walking_time_s`, `stopped_time_s`, `running_distance_m`.

Units: metres, seconds, metres per second, beats per minute, steps per
minute (for `avg_cadence`/`max_cadence` — see the halving rule below), kcal.

Session totals are used where the session has them, and the last record's
values are the fallback:

| field | source | fallback |
|---|---|---|
| `distance_m` | `session.total_distance` | the last record's `distance` |
| `moving_time_s` | `session.total_timer_time` | `total_elapsed_time`, then `last record timestamp - first record timestamp` |
| `elapsed_time_s` | `session.total_elapsed_time` | `moving_time_s` |
| `elevation_gain_m` | `session.total_ascent` | `0` |
| `avg_hr`, `max_hr` | session, truncated to an integer | `null` |
| `calories` | `session.total_calories` | `null` |
| `avg_cadence`, `max_cadence` | session, **not** halved (§4.4) | `null` |
| `avg_speed_ms`, `max_speed_ms` | session | `null` |
| `sport_type` | `session.sport`, normalised | `"running"` |

Sport normalisation: `running`, `trail_running`, `treadmill_running`,
`virtualrun`, `street_running` → `street_running` maps to `running`,
`track_running` → `running`; `walking`, `hiking`, `cycling`, `swimming`,
`strength_training` map to themselves; anything ending in `running` maps to
`running`; anything else maps to itself, lower-cased with spaces replaced by
underscores.

### 4.2 Classification

Each record is classified from **its own speed and its own stored cadence**
(`speed` in m/s, `cadence` exactly as stored in the file):

1. speed is present and `speed < 0.30` → `stand`
2. stored cadence is present and `stored cadence == 0` → `stand`
3. stored cadence is present and `stored cadence < 60` and (speed is absent
   or `speed < 2.2`) → `walk`
4. speed is present and `speed < 1.55` → `walk`
5. otherwise → `run`

The kinds are exactly the strings `"run"`, `"walk"`, `"stand"`.

### 4.3 Intervals, totals and segments

* Sample *i* owns the interval from its timestamp to the next sample's
  timestamp. The last sample owns no interval.
* The interval's kind is the kind of sample *i*. A hole in the stream is
  therefore charged to the sample *before* the hole.
* `running_time_s`, `walking_time_s`, `stopped_time_s` are the sums of those
  intervals per kind, rounded to **one decimal place**.
* `running_distance_m` is the sum of the distance increments
  (`distance[i+1] - distance[i]`, when both are present and the increment is
  positive) whose *left* sample is a `run`, rounded to **one decimal place**.
* `import.segments` merges consecutive samples of the same kind. Each segment
  is `{kind, start_s, end_s, samples, duration_s}`:
  * `start_s` = the elapsed time of the first sample of the group,
  * `end_s` = the elapsed time of the **last sample of the group** (not the
    end of its interval),
  * `samples` = the number of samples in the group,
  * `duration_s` = `end_s - start_s`, rounded to three decimals.

  A group of *n* one-second samples therefore has `duration_s = n - 1` while
  the totals count *n* seconds. That is the reference behaviour (§10.3).

### 4.4 Cadence halving

Some devices store running cadence as stride cycles (two footfalls), so the
file says 78 and the watch displays 156 spm.

```
halved_cadence(value, sport):
    if sport is not None and sport not in {running, trail_running,
            treadmill_running, street_running, track_running, virtualrun}:
        return value
    return value * 2 if 0 < value < 100 else value
```

The correction applies to the **lap** cadence and the **cadence stream**. It
does **not** apply to:

* the classification (§4.2), which uses the stored value;
* `activity.avg_cadence` / `activity.max_cadence`, which are the session
  values as stored (§10.2).

`sport` here is the raw FIT `session.sport` string, not the normalised
`sport_type`.

### 4.5 Streams

Only `run` samples contribute. For each stream the `seconds` array is
`int(round(timestamp - first_record_timestamp))` and `values` are the raw
values, in file order. The streams are:

| kind | unit | value |
|---|---|---|
| `hr` | `bpm` | heart rate |
| `cadence` | `spm` | halved cadence (§4.4) |
| `pace` | `s/km` | `1000 / speed`, only where `speed > 0.1` |
| `distance` | `m` | cumulative distance |
| `elevation` | `m` | altitude |

A stream whose filtered list is empty is still present in the activity, with
empty `seconds` and `values` arrays (this happens for `cadence` when the
watch has no cadence sensor). The persistence layer drops empty streams.

### 4.6 Laps

The FIT laps are rebuilt over the running samples of each lap's window
(`elapsed_s` is the cumulative sum of the laps' `total_elapsed_time`):

* `duration_s` = the sum of `t[i+1] - t[i]` over consecutive pairs where
  **both** samples are `run`, rounded to three decimals.
* `running_distance_m` = the distance increments over those same pairs,
  rounded to two decimals.
* `avg_speed_ms` = `running_distance / running_time`, **not rounded**.
* `avg_hr` = the mean of the running samples' heart rates, truncated to an
  integer; `max_hr` = the maximum, truncated to an integer.
* `avg_cadence` = the mean of the running samples' halved cadence, rounded to
  one decimal; `max_cadence` = the maximum, rounded to one decimal.
* `pace_s_per_km` = `running_time / (running_distance / 1000)`, rounded to two
  decimals; `null` when the running distance is not above 1 m.
* `elapsed_s` = the lap's original cumulative elapsed span, rounded to three
  decimals.
* `distance_m`, `max_speed_ms`, `elevation_gain_m`, `elevation_loss_m`,
  `stride_length_m`, `start_elevation_m`, `end_elevation_m` are carried over
  from the FIT lap unchanged.

`import.lap_bounds` is the cumulative sum of the FIT laps'
`total_elapsed_time`, rounded to three decimals.

### 4.7 `import.samples`

One row per record message, in file order:

```jsonc
{ "index", "elapsed_s", "kind", "distance_m", "speed_ms", "stored_cadence",
  "cadence_spm", "heart_rate_bpm", "altitude_m" }
```

`elapsed_s` is the sample's timestamp minus the first sample's timestamp.
`stored_cadence` is the value as stored in the file; `cadence_spm` is the
halved cadence (§4.4) or `null`. `altitude_m` is `null` when the record has
no altitude.

### 4.8 `import.geo_points`

`{count, first[3], last[3]}` — the first and last three decoded GPS points,
each `[latitude, longitude]` in degrees (§2.1).

## 5. The fingerprint

The reference pipeline is: persist the activity (`store_activity`), then
`compute_fingerprint`. The golden file records the inputs to the fingerprint
(`fingerprint.inputs`) and its result (`fingerprint.fingerprint`).

### 5.1 Inputs

* `max_hr_reference`: the largest `max_hr` over the athlete's activities
  (190 when there is none). The golden cases each have exactly one activity,
  so the reference is that activity's `max_hr`.
* `zone_model`: five zones with boundaries at `reference × {0, 0.6, 0.7, 0.8,
  0.9}` and the names `Recovery`, `Aerobic`, `Tempo`, `Threshold`,
  `Anaerobic`. The last zone has no upper bound (`null`).
* `lap_count`, `athlete_id` (`null`), `activity_source`.

### 5.2 The computation

Let `laps` be the activity's laps sorted by `lap_index`, after dropping the
laps that look like walking: a lap is dropped when its `avg_cadence` is
present and above zero and **below 125**, and its `avg_speed_ms` is absent or
**below 2.2**. If that would drop every lap, all laps are kept.

With `third = len(laps) // 3`: `first = laps[:third]`, `last = laps[-third:]`
(both empty when `third` is 0), and `half = len(laps) // 2` splits the laps
into two halves.

| field | definition |
|---|---|
| `cadence_avg` | mean of the laps' `avg_cadence` (values > 0 only) |
| `cadence_cv` | `stdev / mean × 100` of the laps' `avg_cadence`; `null` unless there are at least 3 values and the mean is above 0. `stdev` is the *sample* standard deviation (n − 1). |
| `cadence_drift_pct` | `(mean(last cadence) − mean(first cadence)) / mean(first cadence) × 100`; `null` if any part is missing |
| `hr_avg` | the activity's `avg_hr` if it is above 0, else the mean of the laps' `avg_hr`, else the mean of the `hr` stream values |
| `hr_max` | the maximum over the laps' `max_hr` and the activity's `max_hr` |
| `hr_drift_pct` | `(mean(last hr) − mean(first hr)) / mean(first hr) × 100` |
| `hr_drift_bpm` | `mean(second half hr) − mean(first half hr)` |
| `pace_drift_pct` | `(mean(second half pace) − mean(first half pace)) / mean(first half pace) × 100` |
| `first_half_hr`, `second_half_hr` | the means of the halves' `avg_hr` |
| `first_half_pace_s_km`, `second_half_pace_s_km` | the means of the halves' paces |
| `efficiency_first`, `efficiency_last` | see below |
| `decoupling_pct` | `(efficiency_first − efficiency_last) / efficiency_first × 100`; `null` if either efficiency is missing |
| `pace_cv` | `stdev / mean × 100` of the laps' paces, over the *pace laps*: all laps, unless the last lap's distance is below 15 % of the activity's distance, in which case the last lap is dropped. `null` unless at least 3 values and a positive mean. |
| `negative_split_pct` | `100` when the last third's mean pace is below the first third's, else `0`; `null` if either is missing |
| `stride_length_cm` | mean of the laps' `stride_length_m` (values ≤ 3 m) × 100; `null` when there are none |
| `form_score` | see below |
| `zone_distribution` | see below |
| `running_time_s`, `walking_time_s`, `stopped_time_s` | copied from the activity |
| `notes` | `"Synthetic demo activity."` for a demo activity, else `null` |

**Pace of a lap** = `duration_s × 1000 / distance_m` when both are present and
above zero, else `1000 / avg_speed_ms` when the speed is present and above
zero, else the lap has no pace.

**Efficiency factor** (Minetti, speed-based — *not* pace-based) for a group of
laps:

```
paired   = the group's laps that have a pace and an avg_hr above 0
pace     = mean of the paired laps' paces
hr       = mean of the paired laps' avg_hr
speed    = 1000 / pace
EF       = speed / (hr / max_hr_reference)
```

`null` when there are no paired laps, no pace, or no heart rate.

**Form score**:

```
components = [(30, cadence_cv, 15), (45, max(0, decoupling_pct), 25), (25, pace_cv, 25)]
present    = the components whose value is not null
quality(w) = clamp(1 − value / limit, 0, 1)
form_score = sum(weight × quality) / sum(weight) × 100
```

Missing components are excluded and the weights are renormalised over the
components that remain. `null` when nothing remains.

**Zone distribution**: if the activity has zone rows, they are used
(`{zone_no: seconds}`). Otherwise the zone model (§5.1) is used and each lap's
`duration_s` is added to the **first** zone whose bounds contain the lap's
`avg_hr` (`low ≤ hr < high`; the open-ended zone matches anything above its
low bound). Zone keys are the zone numbers as strings.

## 6. Readiness

`compute_readiness(day)` for one day, over the physiology rows of a database.

### 6.1 Baselines

The rows of the **30 calendar days before** the day (the day itself is
excluded), with values above zero only:

* `sleep_s` → the **median**
* `hrv_ms` → the **mean**
* `resting_hr` → the **mean**

No history means no baseline: the driver is then unavailable rather than
scored against a population default.

### 6.2 Drivers

| key | label | weight | value | quality |
|---|---|---|---|---|
| `sleep` | Sleep | 25 | `sleep_s / 3600` (hours) | `value / baseline_hours` |
| `sleep_score` | Sleep score | 10 | the row's score | `score / 100` |
| `hrv` | HRV | 25 | `hrv_ms` | `hrv / baseline` |
| `resting_hr` | Resting HR | 15 | `resting_hr` | `1 − (rhr − baseline) / (0.2 × baseline)` |
| `stress` | Stress | 10 | `stress_avg` | `1 − stress / 100` |
| `body_battery` | Body battery | 10 | `body_battery_avg` | `battery / 100` |
| `load` | Load | 5 | `acute_load / chronic_load` | `1 − max(0, ratio − 1.3) / 1.3` |

A driver is **dropped** when its value is missing, when its quality is missing
(the personal drivers need a baseline), or when the value is not a number
≥ 0. A dropped driver contributes nothing to the weights.

* `contribution` (raw) = `weight × clamp(quality, 0, 1)`
* `score` = `sum(contributions) / sum(weights) × 100`, rounded to **two
  decimals**; `null` when there are no drivers
* the reported `contribution` of each driver = `raw / sum(weights) × 100`,
  rounded to **two decimals**
* `grade`: `peak` (≥ 85), `good` (≥ 70), `fair` (≥ 50), `low` (below 50), or
  `unknown` when there are no drivers

Each driver also carries `unit`, `baseline` (the personal baseline, `null` for
the scale-based drivers), `delta` (`value − baseline`, `null` for the
scale-based drivers) and a human-readable `detail` string. The `detail`
strings are part of the contract; they are formatted as follows:

* sleep: `"7h45m vs 7h30m baseline"`, or `"Personal sleep baseline unavailable"`
* sleep score: `"Garmin sleep score out of 100"`
* HRV: `"58.0 ms vs 55.0 ms baseline"` (one decimal place)
* resting HR: `"47.0 bpm vs 48.1 bpm baseline"` (one decimal place)
* stress: `"Average daily stress; lower is better"`
* body battery: `"Average daily body battery out of 100"`
* load: `"Acute/chronic load; ratios above 1.3 reduce readiness"`

`recommendation` and `rationale` are fixed strings per grade; `rationale` names
the two drivers with the largest deduction (`weight − contribution > 0.01`),
or says that the available drivers are at their reference levels, or that no
usable data exists.

## 7. The plan engine

### 7.1 Matching

For each planned session (in date order) the engine picks an activity:

1. candidates are the activities within ±2 days of the session's range,
   not yet claimed by another session;
2. an activity whose `local_date` equals the session's date and whose
   `sport_type` is a run sport wins (ties broken by the smallest distance in
   days to the session's date);
3. for a `rest` or `strength` session, an activity on the same date that is
   **not** a run sport wins (for `strength`, its `sport_type` must contain
   `"strength"`);
4. otherwise, a run activity within ±2 days wins (closest date first, then
   closest distance to the target);
5. a claimed activity is used by at most one session.

Run sports: `running`, `trail_running`, `treadmill_running`, `virtualrun`,
`street_running`, `track_running`, `walking`, `hiking`.

### 7.2 The verdict

`verdict_for(session, activity)`:

```
actual   = activity.distance_m (null when there is no activity)
target   = session.target_distance_m (null when the session has no target)
pace     = activity.moving_time_s / (activity.distance_m / 1000)   # seconds per km
band     = pace is within [pace_low_s_km, pace_high_s_km]; a missing bound is unbounded;
           null when the session has neither bound
distance_hit = actual is not null and (no target
               or actual >= target × 0.95
               or |actual − target| <= actual × 0.05)
```

The verdict is the first of these that applies:

1. no activity → `missed`
2. the session is `rest` or `strength` **and** the activity is a run sport →
   `substituted`
3. the session is `tempo` and the activity looks like an interval →
   `substituted`
4. the session is `interval` and the activity is longer than 14 000 m **and**
   more than 1.25 × the target → `substituted`
5. there is a target and `actual < target × 0.8` → `short`
6. `distance_hit` and the band is not met → `missed_pace`
7. `distance_hit` → `hit`
8. otherwise → `short`

An activity "looks like an interval" when it has at least three laps of at
least 400 m with a positive duration, or when its name contains `interval`,
`repeats` or `fartlek` (case-insensitive).

`adherence_score` = `round(0.5 × distance_score + 0.4 × pace_score + 0.1 ×
type_score, 1)`, and `null` when there is no activity:

* `distance_score` = `clamp(actual / target × 100, 0, 100)`; 100 when there is
  no target
* `pace_score` = 100 when there is no band; 100 when the band is met; else
  `max(0, 100 − min(|pace − band_edge| / 60 × 10, 100))` where `band_edge` is
  the lower bound if present, else the upper bound
* `type_score` = 0 when the verdict is `substituted`, else 100

`distance_delta_m` = `actual − target`, or `null` when there is no target.
`pace_delta_s_km` = `pace − mean(of the bounds that exist)`, or `null` when
there is no activity or no bound.

A `rest` session with no activity is **overridden** to `hit`, with
`distance_hit: true`, `pace_band_hit: null` and `adherence_score: 100.0`: a
logged absence is the intended outcome of a rest prescription.

### 7.3 The cause

A cause is only produced for a session that did not go to plan; a `hit` has
no cause (`null`, `null`).

* no activity → `"No activity was logged for the planned session."`,
  confidence `0.0`
* no physiology → `"Physiology data is unavailable, so the reason for this
  result is unknown."`, confidence `0.0`
* otherwise the factors are collected and sorted by confidence, descending:

  | factor | condition | confidence |
  |---|---|---|
  | `short sleep` | the day's sleep is more than an hour below the baseline | 0.85 |
  | `elevated fatigue` | the day's HRV is below 90 % of the baseline | 0.7 |
  | `illness or overreaching` | the day's resting HR is more than 4 bpm above the baseline | 0.6 |
  | `mechanical inefficiency` | this run's cadence CV is above the mean of the previous 30 days' cadence CVs | 0.55 |
  | `intended race-week load` | a `race` session whose pace is outside its band | 0.55 |

  With factors: `"Likely influenced by <first> and <second>."`, with the
  confidence of the **highest** factor.
  Without factors but with baselines: `"No measured factor explains the result;
  it may reflect a fitness gap or an off-plan effort."`, confidence `0.2`.
  With physiology but no baselines: `"Physiology is available, but there is not
  enough baseline data to explain this result."`, confidence `0.1`.
  Otherwise: `"Physiology data is unavailable, so the result is unexplained and
  may reflect fitness or an off-plan effort."`, confidence `0.1`.

### 7.4 Adherence

`adherence(from, to)` returns:

* `overall_pct` = `round(hit-or-missed_pace sessions / all sessions × 100, 1)`
* `planned_km` = the sum of the targets, rounded to two decimals
* `actual_km` = the sum of the matched activities' distances, rounded to two
  decimals
* `planned_sessions`, `completed_sessions` (a matched activity),
  `hit_sessions` (`hit` + `missed_pace`), `missed_sessions` (`missed`),
  `extra_sessions` (run activities that no session claimed)
* `by_verdict`: the count of each of `hit`, `missed_pace`, `short`, `missed`,
  `substituted`
* `rows`: one row per ISO week, in date order: `week_key` (`YYYY-Www`),
  `start_date` (the Monday), `phase` (`null`), `planned_km`, `actual_km`,
  `planned_sessions`, `completed_sessions`, `missed_sessions`, `hit_sessions`,
  `delta_km` (rounded to two decimals), `adherence_pct` (rounded to one
  decimal)

### 7.5 A session whose kind is not known

A session may carry the kind `unknown`: nothing in the imported document
named a kind of session, so the importer says so rather than guessing
`easy`.

`unknown` is **not** one of the kinds a plan may prescribe — it is the
absence of one — so:

* it gives a run no plan intent, and a comparison that has one falls back
  to distance and says so;
* it is not `rest`, so a logged absence is not the `hit` a rest day earns;
* it is not `tempo`, `interval`, `long` or `race`, so no substitution rule
  and no cause applies to it;
* the verdict is the distance verdict — `hit`, `missed_pace`, `short` or
  `missed` — according to what was logged and what the session prescribed.

The import paths accept `unknown`. The kinds a plan may prescribe are the
eight of `SESSION_TYPES`.

## 8. Comparison rules and tolerance

A port's output is accepted when, for every path in the golden file:

* **strings, booleans, `null` and integers** are exactly equal;
* **floating point numbers** differ by at most
  `1e-9 × max(1, |golden value|)`.

That tolerance exists because the golden generator rounds every float to ten
decimal places (§9), so the last digits of a double are not part of the
contract. Everything the reference implementation itself rounds (§4, §5, §6,
§7) is rounded by the port in the same place and then compared exactly.

Where the reference rounds, the port must round the same way:

| value | rounding |
|---|---|
| `running_time_s`, `walking_time_s`, `stopped_time_s`, `running_distance_m` | 1 decimal, half-even as Python's `round` |
| segment `start_s`, `end_s`, `duration_s`, `lap_bounds`, lap `elapsed_s` | 3 decimals |
| lap `running_distance_m` | 2 decimals |
| lap `avg_cadence`, `max_cadence` | 1 decimal |
| lap `pace_s_per_km` | 2 decimals |
| GPS degrees | 7 decimals |
| readiness `score`, driver `contribution` | 2 decimals |
| `adherence_score` | 1 decimal |
| `overall_pct`, `adherence_pct` | 1 decimal |
| `planned_km`, `actual_km`, `delta_km` | 2 decimals |

Python's `round()` is *banker's* rounding (ties to even); a port that rounds
halves away from zero will differ on exact ties. The golden values contain no
exact ties, so this does not arise in practice — but a port that wants
bit-identical doubles must implement round-half-to-even.

## 9. Determinism

The golden files are byte-stable. The generator guarantees it as follows:

1. **Timezone.** `TZ=UTC` is pinned by the harness before the reference
   implementation is imported. The FIT importer is timezone-sensitive
   (§10.1), so this is required, not cosmetic.
2. **No clock, no randomness.** The FIT fixtures are built from literal
   values; the physiology rows are literal values; the plan block is literal.
   Nothing reads the current time.
3. **Float normalisation.** Every float in the golden output is rounded to ten
   decimal places (values of magnitude ≥ 1e6 keep their full precision). This
   removes the last-ULP noise that a different summation order could produce.
4. **Key order.** Object keys are emitted in a fixed order and are never
   sorted, so the files diff cleanly.
5. **No timestamps in the output.** `computed_at` and `created_at` are
   deliberately absent from the golden files.
6. **Isolated state.** The harness runs against a throwaway SQLite database
   and a throwaway `STRIDE_DATA_DIR`; the athlete's real data is never read.

## 10. Observed reference behaviour that looks wrong

These are **notes about the reference implementation**, not requirements. They
are listed so that a port author does not "fix" them silently and end up with
numbers that disagree with the Python reference. If any of them is fixed in
the reference, the golden files must be regenerated in the same commit.

1. **FIT timestamps are converted through the host timezone.** `fitparse`
   returns naive datetimes, and the importer calls `.timestamp()` on them,
   which interprets them as local time. The same file therefore yields a
   different `start_time` and possibly a different `local_date` on a host in
   another timezone (in IST the activity moves back 5 h 30 m and can change
   its date). The harness pins `TZ=UTC`; a port should treat FIT timestamps as
   UTC.
2. **The activity's `avg_cadence` is not halved**, while the laps' and the
   cadence stream's are. A run stored at 78 spm reports `avg_cadence: 78.0`
   and lap cadences of 156.
3. **A segment's `duration_s` excludes its last interval**, while the time
   totals include it (§4.3).
4. **A hole in the record stream is charged to the sample before it.** A
   watch that was paused for 100 s while running adds 100 s to the running
   time (see the `gaps` case).
5. **The fingerprint's pace uses the lap's total distance with the running
   time.** `pace = duration_s × 1000 / distance_m`, where `duration_s` is the
   running-only time and `distance_m` is the lap's full distance — so a lap
   that was partly walked gets a pace that is too slow.
6. **The zone distribution uses the lap's average heart rate**, not the
   per-sample heart rate, so a lap that crossed a zone boundary is counted
   entirely in one zone.
7. **`max_hr_reference` is the maximum over the athlete's activities**, not a
   fixed value, so the reference — and therefore the zone boundaries and the
   efficiency factor — moves as the athlete's history grows.
8. **A session's `sport_type` is the raw FIT sport**, so a treadmill run is
   `running`, not `treadmill_running`: the importer ignores `sub_sport`.
