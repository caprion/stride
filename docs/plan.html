01 The product in one page

Stride is a private, local-first running log for one athlete. It exists to answer one question every morning and one question every evening: what should I do today, and what did that last run actually mean? Everything else in the app is evidence for those two answers.

The loop

Plan → Execute → Understand → Adapt. The plan is a first-class object: every session is measured against the intent that produced it. The app records what happened next to what you intended — it never tells you whether you were right.

The promise

"Your data stays on this phone." One credential (a Garmin Personal API key) lives in the Android Keystore. No account, no cloud, no server to reach. Works on a plane.

The difference

Most running apps tell you what you did, and some tell you what you should have done. Stride does neither: it shows you your own numbers against your own normal, what usually happens on days like this, and — if you want one — an easier option. The decision stays with you.

The four destinations (constant at every width)

The IA is fixed. Width changes the arrangement, never the set. Compare and Plan are reached contextually, so the destination count stays at four on a 360 px phone and on a 1280 px browser.

TodayRunsProgressBody + Compare (from any run)+ Plan week (from Today)

The one rule that kills the old repo's churn: if a screen cannot exist on the phone, it does not exist. The desktop is the same four destinations with more room — it never grows its own features. This single rule retires the entire class of problems the old repo suffered from (desktop-only Compare, the training calendar, /connect, the pairing ceremony).

What the desktop is, precisely

It is

  • the dev rig — the fast feedback loop (edit → reload → see it in 3 seconds, not 3 minutes)
  • the reference host — the process the MCP/agent harness queries and the parity differ runs against
  • the community tool — published, cloneable, buildable by a stranger in one command

It is not

  • not a distributed product — no store, no SLA, no feature parity promise
  • not a place with its own screens
  • not a second implementation of anything — it hosts the same Rust core

03 Architecture

One domain implementation, two hosts, zero Python. The phone and the desktop are the same crate graph — the phone reaches it in-process through a small FFI, the desktop reaches it over loopback HTTP. There is no second implementation of the domain, and therefore nothing that can drift.

3.1 The workspace

CrateOwnsMust never
stride-coreDomain types and units; plan engine; recovery & readiness; run story; fitness & progress maths; compare. Pure: no I/O, no clock, no randomness.Touch SQLite, HTTP, or the system clock. Everything time-dependent takes an injected clock — that is what makes the golden corpus reproducible.
stride-ingestGarmin Personal API client (token exchange, zip download, size caps, one-retry 401); the FIT decoder; run/walk/stand segmentation.Decide what a number means (that is core's job), or write to the store.
stride-storeSQLCipher schema, migrations, repositories, FIT blob storage, export/import.Log, return or persist the database key. The key comes from the caller and never comes back out.
stride-apiThe single router, DTOs, response shapes, the FFI surface, the trust gate.Contain domain logic — it translates, it does not decide.
stride-testkitThe frozen golden corpus, fixture builders, the parity differ harness, viewport/UI assertion fixtures.Be imported by a product crate (it is a dev-dependency everywhere).
desktopOne binary: static SPA bundle + router + trust model + local key store.Grow a feature of its own.
android/…/stride-ffiUniFFI bindings, panic catching, JSON in / JSON out.Let a panic cross the boundary. The FFI is the only place unsafe is allowed.

Dependency rule: the graph is a DAG and it stays one — core ← ingest, core ← store, api → core, ingest, store. No cycles, no horizontal edges.

3.2 Two hosts, one core

Phone (the product)

Kotlin shell + Capacitor WebView hosting the React app. The WebView calls plugin.apiCall(path, body); the plugin hands the path to the Rust core in-process. No HTTP, no port, no server. The Garmin key is unwrapped by the Keystore inside the native layer and never enters JavaScript.

Desktop (the rig / community tool)

One Rust binary. It opens the encrypted database, serves the embedded React bundle, and exposes the same router over loopback HTTP (plus an explicitly trusted CIDR list). It is the same crate graph — the desktop binary and the APK cannot disagree about a number.

3.3 The data flow of one sync

  1. Key exchange — Personal API key → OAuth1 token pair → 24-hour JWT. The key is stored encrypted; the JWT is disposable and re-minted on demand.
  2. Index pull — activity list + wellness list for the missing window, with a cursor. The cursor is stored after a successful parse, never before.
  3. Download — the activity zip (ZIP-slip-safe member validation, absolute paths rejected, size caps).
  4. Decode — FIT → per-second series + events. Sentinel values mean "no value" and must never be read as numbers.
  5. Derive — segmentation, fingerprint features, per-activity metrics. This is where FIT is kept as the source of truth: the original file is stored, and every derived series is recomputable.
  6. Persist — SQLCipher transaction; the activity, its metrics and the FIT blob land together or not at all.
  7. Re-derive the views — plan/recovery/progress are computed on read from stored primitives, so a change to the engine needs no re-sync.

Why "compute on read" instead of "precompute a score column": because the engine will change during the migration, and a stored score silently rots. The old repo's stale-golden bug came from exactly this shape. The cost is CPU; the benefit is that the score always matches the current engine.

04 The screen system: one IA, every width

The old repo branched the app by device class (isNativeApp()) and produced two information architectures that then had to be kept in sync. v2 branches by width and produces one architecture with several arrangements.

4.1 Width bands

BandWidthNavigationShape of a screen
Compact< 600 pxBottom tab bar (4), thumb-reachableOne column. Cards stack. Tables become metric rows. Charts are full-bleed with a horizontal scroll inside the chart only.
Medium600–1023 pxBottom tab bar → collapses to a top barOne column capped at ~680 px, centred; two-column only where a card pair is genuinely independent.
Wide≥ 1024 pxLeft rail (4 destinations + secondary links)Content column max ~880 px; charts may sit side by side; Compare shows two columns.

Bands are decided by container width (CSS container queries), not viewport width — so a phone in split-screen, a foldable unfolded, or a browser window resized mid-session all land in the right band without a reload.

4.2 The reflow rules (these are the contract)

  • Set constant, arrangement fluid. The four destinations are identical at every band. A test asserts the destination set at every viewport, so a desktop-only screen cannot reappear by accident.
  • Nothing scrolls sideways except a chart's own series. No page-level horizontal scroll, ever, at any width.
  • Tap targets ≥ 44×44 px at compact; ≥ 32 px at wide (mouse).
  • Type scales with the band, not the device — 16/14/13 for body at compact, 15/13/12 at wide (denser is fine when there is room).
  • Safe areas are respected via env(safe-area-inset-*); the compact tab bar sits above the home indicator; the old repo's Capacitor safe-area injection bug is fixed at the source, not worked around.
  • Heights use dvh, not vh — mobile browser chrome must not clip the last row.
  • No device sniffing for layout. A build-time flag exists only for genuinely native capabilities (hardware back button, Keystore screen, share sheet).

05 Screen specifications

Every screen below is specified before code: its purpose, the question it answers, what it must never do, its content blocks at each width, the data behind it, its interactions, its states, and the checks that prove it works. This is the document the implementation is measured against.

Todaydestination 1 of 4the reason the app exists

Why

Today is a readout, not an instruction. It tells the athlete where they stand this morning — their own numbers, against their own normal — in the plainest language a human would use, and then stops. The athlete decides what to do; the app's job is to make the decision informed.

What it must never do

  • Never instruct. No "take the day", no "go easy", no "you should", no imperative addressed to the athlete. The old product's graded advice ("keep it easy today") was a judgement dressed as a suggestion — v2 drops it.
  • Never grade, score or rank the athlete. No red "missed", no readiness score, no "you are behind".
  • Never draw a conclusion from the vitals — no "you are not recovered", no "you are ready". Report each vital's direction; the athlete reads the combination.
  • Never link an option to a vital ("because your sleep was low, there's an easy one") — that link is the judgement.
  • Never rank or prefer the options it offers — no "recommended" chip, no highlighted choice.
  • Never show two different numbers for the same thing (the old repo's Today and Body disagreed; the core owns the values and both screens read them).
  • Never show a percentage the data cannot support (a near-zero baseline yields no percentage).
  • Never show a raw σ or z — the human value and the human comparison, in words.

Content blocks

  1. The vitals — the primary content, always first: sleep, HRV and resting HR as rows of value + direction. Sleep — 6 h 10 m — could be better · 1 h 10 m less than your usual. The direction word comes from the closed set; the arithmetic is secondary and muted; nothing is scored, coloured or graded.
  2. Rest — one composite line over the three vitals, stated as a count and a direction: Rest — could be better · 2 of 3 signals below your usual. It is a summary of the three, not a verdict about the athlete, and the three rows are always shown beneath it.
  3. Direction of travel — how each vital has moved over the last few days, in words: 3rd night down, up 3 nights, steady.
  4. Today's session — if a plan exists: the intent in name-value form (10 km · easy · from your imported plan). It is the athlete's own plan, shown, not a command. Tap → the Plan week.
  5. The other options — other sessions in the plan, unranked and never linked to the vitals: a 5 km on Friday · a 30-minute one on Sunday. Absent when the plan holds nothing else.
  6. Distance comparison — shown only when the last run differs from the plan's target by more than 10%. Then a neutral line: 12.4 km · 2.4 km more than the 10 km target. Within 10%, the line is absent — a 2% difference is not news, and neither more nor less is good or bad.
  7. Last run — one line: distance, duration, and a link into the detail page.

House style for every value

label · value · direction, in that order, with the unit written out and the direction taken from the closed set. The arithmetic sits behind the direction, muted: "14 below your usual" is arithmetic, not a verdict. Numbers are rounded to what a human would say ("6 h 10 m", not "6.166 h"; "14 below your usual", not "−13.7%"). No abbreviations the athlete has to learn, no jargon, no icons standing in for words, no colour carrying meaning on its own.

States

  • No data yet (never synced): "Connect your Garmin key to see today's numbers" + a connect button. No fake numbers, ever.

  • Stale data (> 36 h): the header says "last synced 2 days ago" and every value carries that date.

Acceptance checks

  • No user-facing string on this screen contains an imperative addressed to the athlete (a CI lint over the string catalogue forbids "should", "must", "take the day", "rest", "go easy", "easy today").

  • No string on this screen links an option to a vital.
  • The distance comparison appears on exactly one fixture (12.4 km against a 10 km target) and on none of the others (10.2 km against 10 km → silent).
  • Today and Body render the same values and directions for the same state (a golden assertion, not a screenshot).
  • Every displayed value is rounded the way a human would say it, and carries its unit.
  • At 360 px: no horizontal scroll; the vitals block is fully visible without scrolling.
Runsdestination 2 of 4the feed

Why

The feed is the athlete's memory of their own running, and the entry point to every explanation. It is a list of activities, not of days, and each row carries a sentence about meaning.

What it must never do

  • Never hide the story line — a row without a sentence is a spreadsheet.
  • Never show a "missed" badge against an activity; activities are facts, not scores.
  • Never load everything — the feed is windowed by date with an explicit "load more".

Content blocks

  1. Group header — "This week" / "12 Oct" — with the group's total (distance, time) at wide widths only.
  2. Activity row — date, title, chips (distance · pace · avg HR · effort), and the story line in one sentence. A route thumbnail at wide widths.
  3. Actions — open the detail page; "Compare with…" (the contextual entry to Compare); "Add a note" (one of the three allowed inputs).
  4. Import entry — a single "Import a FIT file" action (phone: file picker; desktop: drag-and-drop). Dedupe is silent and reported.

Activityreached from Runsthe detail page

Why

A run becomes a lesson here. The screen answers three questions in order: what was it, what did it mean, and how did it compare to my plan and my normal?

Content blocks (in order)

  1. Header — title, date, and the three headline numbers (distance, time, pace).
  2. The story — the same sentence shown in the feed, expanded with the "why" (it sat inside the zone, it was longer than usual, it matched the plan).
  3. Map — route with a start/end marker; at compact the map is a 16:9 banner, not a full-bleed panel.
  4. Effort — heart-rate series with the athlete's own zone bands, and the pace series under it, aligned on the same x-axis (the two charts are the same time axis — this is the single most useful view in the app).
  5. Splits — per-kilometre table; at compact it becomes the metric-row form, at wide a real table.
  6. Elevation — an area chart, collapsible (off by default at compact).
  7. Against the plan — a plain comparison, only if a plan existed: "8.4 km run · 8 km planned". No verdict.
  8. Actions — "Compare with…", "Add a note", "Export FIT".

Layout by width

  • Compact: single column; the effort chart is the hero; the map is a collapsible banner; splits collapse to "show splits"; everything is one tap away, nothing is hidden behind a horizontal scroll.
  • Medium: single column capped 680 px; map and effort chart may sit side-by-side above 900 px of content width.
  • Wide: two columns — left: story + splits + elevation; right (sticky): map, effort chart and the plan comparison.

Acceptance checks

  • The headline numbers match the row in the feed and the values in the story sentence (single source, golden assertion).
  • HR and pace charts share an x-axis and are aligned to the second in the DOM.
  • At 360 px the effort chart's axis labels are legible (≥ 11 px effective) and the chart does not overflow its card.
Progressdestination 3 of 4the motivation

Why

Progress shows the athlete's trajectory — forgivingly. A week with nothing in it is a gap in the line, not a failure. The screen's job is to show the trend without ever inventing a trend the data cannot carry, and without ever grading the athlete against it.

What it must never do

  • Never show a percentage change from a near-zero baseline (the old repo's "trend blow-up" bug).
  • Never show a "missed" counter for a week with no plan — only for a plan the athlete set.
  • Never grade consistency ("you are behind", "inconsistent") — state the counts and let the trend speak.
  • Never use a population percentile. Everything is against the athlete's own history.

Content blocks

  1. Headline — "fitter than 8 weeks ago" (or an honest "not enough data yet"), with the evidence in one clause (e.g. "same heart rate, 24 s/km faster").
  2. Weekly volume — a bar chart of the last 12 weeks, with a soft band showing the athlete's typical week.
  3. Pace at heart rate — the honest fitness metric: pace at the same HR over time, with gaps left as gaps.
  4. Bests & milestones — recent bests and the milestones that were actually hit (a 10k, a month, a streak).
  5. Consistency — sessions per week over time, forgiving: a gap is a gap, not a red X.
  6. Adherence — only if a plan exists: a count, not a grade ("7 of 8 sessions run"), with the cause for each session that was not done.

Layout by width

  • Compact: one column; headline first; each chart is a card with a 12-week default range; a range selector (4/8/12/26 weeks) is a segmented control that fits the width without a horizontal scroll.
  • Medium: column capped 680 px; volume and pace-at-HR may be side-by-side above 900 px.
  • Wide: two-column grid: left = headline + volume + pace-at-HR; right = bests, milestones, consistency, adherence.

States

  • Not enough data — the headline says so plainly; charts show what exists with a "needs 4 more weeks" note; no percentage is rendered.
  • No plan — the adherence card is omitted entirely (never "0 of 0 sessions run" against a plan that does not exist).

Acceptance checks

  • A fixture with a zero baseline renders no percentage anywhere on the screen.
  • Adherence is computed against the active plan block only (not every block ever imported — the old repo's duplication bug).
  • The headline sentence's numbers are the same numbers the charts show.
Bodydestination 4 of 4the evidence

Why

Body is where the athlete checks the numbers behind today's readout. It is the same three signals the engine used, shown against the athlete's own normal — and it must show the same values as Today.

What it must never do

  • Never show a 0–100 readiness score (a number the data cannot carry).
  • Never show a population percentile or a device score.
  • Never contradict Today on a number — the values come from the core, once.
  • Never truncate a date label ("Oct 7," was a real bug in the old repo).

Content blocks

  1. The same values as Today, with the history behind them.
  2. Sleep — last night's duration and stage mix, against the athlete's typical night. With no stages, the chart says "duration" and does not draw an empty stage chart.
  3. HRV — the last 30 nights against the personal band (median ± MAD).
  4. Resting HR — the last 30 days against the personal band.
  5. How to read this — two lines of plain text explaining the band. No jargon.
  6. The patterns — the pattern engine over the visible history: your HRV has been below your usual 3 nights this month, on your 6 longest runs this year, your last 3 km was always the slowest. Each carries its sample size. Patterns live here, not on Today.

Layout by width

  • Compact: one column; the three signals lead the screen (not a summary at the bottom); each signal is a card with a 30-point sparkline and the personal band shaded.
  • Medium: column capped 680 px; sleep and HRV may pair up.
  • Wide: three-column signal cards (sleep · HRV · RHR) above a full-width "how to read this" note; the personal band is labelled on the axis.

Acceptance checks

  • Body's values == Today's values for the same state (byte-identical, golden assertion).
  • Every date label renders fully at 360 px (no truncation, no ellipsis).
  • A night with no stage data renders the duration chart only — no empty stage chart.
Planreached from Todaynot a destination

Why

The plan is the intent the engine judges against, so it must be inspectable — but it is not a place the athlete lives in. It is reached from Today and from the feed, and it goes back where it came from.

What it must never do

  • Never label an inferred baseline as "not done" — a baseline is not a prescription.
  • Never write "missed" — the plain fact is that a session was planned and did not happen.
  • Never show two plan blocks at once without naming which is active.
  • Never require a Garmin account to have a plan (v2 has no account flow).

Content blocks

  1. The source banner — Baseline (inferred from your history) · Prescribed (imported) · Typed. Named in plain words, with the "why" available on tap.
  2. This week — seven days, each with intent (distance, type), the actual, and a plain status: done · planned · not done.
  3. Today — highlighted inside the week.
  4. Adherence — a single number plus the count it is made of.
  5. Sources / manage — import a plan (markdown / CSV / JSON / Garmin CSV export). Editing a plan is not in v2.

Layout by width

  • Compact: a 7-column week strip that fits 360 px (each day a 44 px column with the day letter and a dot: done / planned / not done / rest), then the day detail below it, then the month list.
  • Medium: the week strip becomes a 7-column row with numbers; the day detail is below.
  • Wide: a real calendar grid (weeks as rows), the selected day's detail to the right, adherence and sources in a left rail column.

Acceptance checks

  • A baseline plan never renders "not done" (golden assertion over every corpus day).
  • The word "missed" appears nowhere in the app's string catalogue (CI lint).
  • Only the active block's sessions are counted — 7 sessions, not 14 (the old repo's duplication bug).
  • An imported plan with no recognisable workout keywords is labelled unclassified, never "easy" (the old repo's silent guess bug).
Comparereached from any runnot a destination

Why

It is the best screen in the product: it turns "is that better?" into a number. It is also the screen most damaged by a small screen, because the naive form is two columns side by side.

What it must never do

  • Never compare silently — the basis is always named (same distance / same route / same HR band / different).
  • Never show a "winner" verdict when the basis does not support it.
  • Never require horizontal scrolling to see a difference.

Content blocks

  1. The basis banner — "Same distance, 3 weeks apart" / "Same route, different week" / "Different distances — read with care".
  2. The metric diff — the primary form at every width: rows of metric · A · B · Δ.
  3. The charts — at wide widths, two charts side by side; at compact, one chart with an A / B toggle.
  4. The two runs — a compact identity card each (date, distance, the story sentence).
  5. Actions — swap A and B; choose a different run; share the comparison as an image or HTML file.

The metric diff is the canonical form

Compact · 360
Wide · A | B | Δ

Layout by width

  • Compact: the diff rows are the screen; a row expands in place to reveal the two values and the delta; charts are behind an A/B toggle; the run identity cards are two stacked rows.
  • Medium: the diff table widens; A and B columns stay side by side from ~520 px of content width up.
  • Wide: two pinned columns (A left, B right) with the diff column at the right edge; charts side by side under the banner.

Acceptance checks

  • At 360 px every delta is visible without scrolling, and the row labels are not truncated.
  • The basis banner is always present; a fixture that compares different distances shows the caution wording.
  • Swapping A and B flips the sign of every delta (property test over the corpus).
Connectfirst run, phonenative, not a web page

Why

One credential, one screen, one promise. This is the first thing a stranger sees, and it must be the easiest screen in the product to get right — and the hardest to leak.

What it must never do

  • Never let the key enter the WebView — it is typed into a native field and wrapped by a non-exportable Keystore key.
  • Never ask for an account, a password, a code, or a pairing.
  • Never show a wall of text before the field.

Flow

  1. The promise in one line: "Your data stays on this phone."
  2. A native text field for the Personal API key, with a link to Garmin's page to create one.
  3. A single primary button: Connect. → states: Checking… → Syncing… → Connected · 160 runs.
  4. "Not now" — the app opens in an empty but honest state (no fake data, ever).

Layout

  • Phone: a native Kotlin activity, full-screen, one column, the field and the button above the fold at 360×640; the keyboard must not cover the button.
  • Desktop: the same content as a first-run page (/connect) that stands alone — no app chrome, no tabs — and disappears once connected.

Acceptance checks

  • The key never appears in any WebView-reachable surface: asserted by a test over the bridge's route table.
  • A failed key produces a specific, actionable message ("that key was rejected by Garmin") and never a stack trace.
  • The desktop first-run page has zero references to pairing, codes or devices.
Settingssecondaryreachable from the rail / a header menu

Why

Three inputs change what the app should say: the weekly goal, a pause, and a note on a run. Everything else in settings is plumbing.

Content blocks

  1. Weekly goal — one number; a blank means "no goal" (never a default of 0 that reads as a failure).
  2. Pause — start/end date, and a one-line reason (travel / sick / injured). While paused, adherence is suspended and the app says so.
  3. Connection — Garmin status, key identifier (last 4 only), last sync time, a "re-connect" action. Never the key itself.
  4. Import — import a plan file or a FIT file.
  5. Storage — database size, "export a backup", "delete all data" (with a typed confirmation).
  6. About — version, licence, the promise, and where the source is.

Layout

  • Compact: a list of rows, each a tappable group; groups are collapsible; nothing nested deeper than one level.
  • Wide: a two-column settings grid inside the 880 px column; destructive actions are last and visually separated.

Acceptance checks

  • No screen in the app ever renders the Garmin key (a CI grep over the built bundle asserts it).
  • "Delete all data" requires typing the word DELETE and cannot be undone silently.

5.8 The two screens that are not web pages

Two flows stay native because the platform APIs are the point:

  • Connect (phone) — the Keystore field. There is no web fallback: the promise "the key never enters the WebView" would be a lie.
  • Background sync (phone) — WorkManager, with a system notification ("Synced 12 activities"). The WebView is suspended; the core keeps running in the app process.

5.9 The voice: vitals, direction, options — no verdicts

The app shows the athlete's vitals, says which way each one has moved against their own usual, and lists what is on the table. It draws no conclusion. A data dump is not helpful and an app that tells you what to do is judging you; this is the line between them, and it is enforced in CI.

1 · Vital — the measurement

Label, value, unit. Nothing added: Sleep — 6 h 10 m · HRV — 48 ms · Resting HR — 63 bpm. No score, no band colour, no icon standing in for a word.

2 · Direction — which way it moved

How the vital sits against the athlete's own usual, said in plain words. The primary descriptor comes from a closed set — three words, no synonyms, no judgement:

  • better than usual
  • about usual
  • could be better

Beside it, the arithmetic — muted, secondary: 5 above your usual, 1 h 10 m less than your usual. And the direction of travel in words: 3rd night down, steady. The athlete reads it; the app does not conclude from it.

"Usual" is defined once, visibly, and drawn on the chart: the median of the last 30 nights, with the band being median ± 1.5 × MAD (config). Inside the band is "about usual". Which side is the better side is a fact about the measurement, not an opinion: more sleep, higher HRV, lower resting HR. Because the band is drawn on every chart, the athlete can see where the line is — and disagree with it.

3 · Options — what is on the table

Facts about the athlete's own plan, listed unranked, never conditioned on the vitals. This is where "easy" and "very easy" live — as the plan's own vocabulary, present or absent on their own merit.

  • Today — 10 km · easy · from your imported plan
  • Also in your plan — a 5 km on Friday, and a 30-minute one on Sunday

The app does not say which to pick, does not highlight one, and does not say "because your sleep was low". Listing an option because the vitals were poor would be the app judging the vitals — so that link is never made.

4 · Pattern — the history, in the history screen

What usually happened to this athlete, stated as a fact about the past, always with its sample size: "the 5 other times your sleep was this low, you ran 8 km or less." It lives on Body, over the visible history — not on the morning screen, and never next to a suggestion.

What is forbidden

  • Commands — "take the day", "rest", "go easy", "you should", "you need to", "it'd be better to".
  • Verdicts — "good", "bad", "poor", "missed", "behind", "failed", a readiness score, a traffic light.
  • Conclusions — the app never combines vitals into a verdict ("you are not recovered"). It reports each vital's direction; the athlete reads the combination.
  • Ranking the options — never "the best choice today is…", never a highlighted "recommended" chip.
  • Shame — no red, no "should have", no "you were inconsistent".

How it is enforced

  • Every user-facing string lives in one catalogue (strings.toml / JSON), never inline in a component.
  • Each string is typed: vital, direction, option, pattern, or status.
  • A direction string must come from the closed set — better than usual · about usual · could be better — and may not be extended. The lint enforces it.
  • A pattern string must carry its sample size; none is emitted from fewer than three comparable days.
  • A CI lint fails the build on a banned word or construction: should, must, take the day, rest, go easy, missed, bad, poor, fail, behind, ready to, recommended, better to, need to.
  • A golden assertion renders every catalogue entry against every fixture state, so wording cannot drift between screens.

What this buys. The old advice was the product's boldest claim and its most fragile one: every wording change was a review cycle, the "same sentence on two screens" bug kept recurring, and every sentence was a judgement of a person's training on a bad day. Informative language has no such failure mode — a value is either right or wrong, and the golden corpus decides which. It also means the app has nothing to apologise for when the data is thin: it shows the value, says "not enough data for a comparison yet", and stops.

6.3 Error and freshness rules

  • Every response carries a generated_at; the UI shows staleness rather than silently showing old numbers.
  • Business failures are typed: no_plan, stale_data, not_enough_history, garmin_rejected — the UI renders each as a specific sentence, never a generic error.
  • No endpoint ever returns the database key, the Garmin key, a file path, or a credential.

07 Security and the trust model

Local-first does not mean "no security model". It means the model is small, explicit, and auditable.

The credential

  • Phone: typed into a native field, wrapped by a non-exportable Android Keystore AES key, stored in noBackupFilesDir, never in the WebView, never in the database, never in a log.
  • Desktop: stored in the OS keyring-equivalent (a file with 0600 in the user's data dir, or an env var for CI); the app reads it, never returns it.
  • The Garmin access token is short-lived (24 h) and disposable: a 401 triggers exactly one re-exchange and one retry, never a loop.

The database

  • SQLCipher, key supplied by the caller, never logged, never returned by an endpoint, never written to a state file.
  • The desktop converts a legacy plain database on first run and keeps a plain backup beside it — with an explicit, documented path.
  • Every query is parameterised; there is no string-built SQL anywhere in the tree (a CI grep asserts it).

The desktop trust model (documented in ten lines)

CallerResultRule
loopback (127.0.0.1 / ::1)allowedalways; no configuration, no ceremony
an explicitly trusted networkallowedSTRIDE_TRUSTED_NETWORKS=100.64.0.0/10,192.168.1.0/24 — the peer address must be inside a listed CIDR
anything elserefused401 with a message naming the env var; no pairing code exists to mint

Why this is the whole model: the data is on the machine, the key is in the machine, and the only exposure is someone on the network reading your own runs. There is no account to phish, no session to steal, no device to revoke — and nothing to explain to a stranger who clones the repo.

Never reintroduce: pairing codes, QR codes, device tokens, capability cookies, remote minting. The old repo spent a day deleting exactly these and they are the single biggest source of "the app wants an account" anxiety. A CI grep asserts that the strings pair-code, pairing and qr do not appear in the route table.

08 Open-source posture

Everything is public: the code, the corpus, the CI, the release pipeline. That is a promise with a bill attached, and the bill is paid in the design.

Licence

AGPL-3.0. It is the licence that matches the product: anyone may run it, fork it, improve it — but if someone offers it over a network, they must publish their source. That protects the "there is no cloud version of Stride" promise with teeth instead of a README sentence.

Repository

Created public, on day one, with the privacy gate already wired. Retrofitting openness onto a repo with history means a history scrub; the old repo's history already contains the athlete's own coordinates from the demo-seed incident.

Support

A SUPPORT.md that says it plainly: "Issues welcome. Features are mine." One athlete's roadmap, everyone's bug reports.

The old repo's CI is not fork-safe and must not be copied. In android.yml the APK job fetches the signing key from repository secrets; on a pull request from a fork those secrets do not exist, so every outside contributor's build fails. It also grants contents: write at workflow level, including to pull requests. v2's workflow: permissions: contents: read globally; secrets only in the release job; pull requests from forks build a debug APK with no signing; releases only from upstream tags.

What ships in a release

  • The APK — signed, arm64, with the certificate fingerprint committed in assetlinks.json so the app installs as a real app, not a browser tab.
  • The desktop binary — one file, per platform, plus the source (which is the point of the licence).
  • Generated release notes — derived from the canonical install document, so the notes cannot describe a flow that no longer exists (the old repo's release notes still told people to run a deleted pairing command).

Working rules for the migration

  • The old repo is the oracle until parity is 100% — the differ runs in CI on every slice, and the old Rust core is retired only when no fixture disagrees.
  • One slice at a time. No two features in flight in the same area of the tree.
  • Every slice ships — the gates run on the slice, and the phone APK is rebuilt for the end-of-slice check.
  • No Python in the new tree. The frozen corpus is data, not code.
  • Each slice's acceptance is a golden assertion where possible — not a screenshot, not a human read.
